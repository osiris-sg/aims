## Xero — two distinct services

### Push: `src/common/xero.service.ts` + `/xero` controller

- `XeroClient` (`xero-node@13`); OAuth flow at `GET /xero/connect?organizationId=` → `GET /xero/callback` where **`state` carries the organizationId**; redirects back to `/portal/integrations`.
- Tokens persisted per-org in `XeroConnection` (access, refresh, expiry, tenantId); this service refreshes on its own paths.
- `upsertDocumentInvoice()` is the full-fidelity editor "Sync to Xero": ACCREC vs ACCPAY, real dates, per-line `accountCode`/`taxType`, Exclusive/Inclusive/NoTax line amounts, explicit per-line tax for rounding parity, in-place updates via `xeroId`, contact get-or-create.
- Flags: `enableXeroIntegration`, `enableXeroDocSync`. Doc: `api-server-production/XERO_INTEGRATION.md`.

### Pull: `src/xero-sync/` (`/xero-sync`)

Explicitly PULL-only mirror. Phase A syncs the **chart of accounts** (upsert by Xero AccountID — new Xero accounts surface as unmapped `XeroAccountMapping` rows for approval, never auto-created) and **contacts** (split into Customer/Supplier by flags). Phase B (invoices/bills/payments/journals) is deliberately deferred to avoid double-counting.

- Token handling differs from the push service: expired token → 401 "re-connect", no auto-refresh; no connection → 424.
- Routes: `status`, `runs`, `POST run` (scoped), `account-mappings` list/patch/create-aims/auto-map (Anthropic-driven). Permissions `xerosync:read|create`.
- `XeroAccountMapping.source` distinguishes AI-suggested from manually-confirmed so auto-map never clobbers manual work. Each "Sync Now" logs an `XeroSyncRun`.

<Note>
Xero operational gotchas (from production reconciliation work): Xero silently ignores edits to paid bills; new Xero apps get granular scopes only (no `accounting.journals.read`); dual-system data changes should complete the AIMS pass first and touch Xero only after explicit approval.
</Note>

## Email — Resend (`src/email/`)

`RESEND_API_KEY`, `RESEND_FROM_EMAIL`, `ADMIN_EMAIL` (default CC). Two flows: `sendInvoiceEmail` (HTML template, TO/CC/BCC, PDF attached, "Click to Pay" button when a payment link exists) and `sendServiceReportEmail`. Only invoices and quotations can be emailed from the editor. Warns rather than throws when the key is absent.

## S3 (`src/common/services/s3.service.ts`)

`@aws-sdk/client-s3`; region `ap-southeast-1`, bucket `RESOURCE_BUCKET` (default `aims-osiris`). Stores generated PDFs, uploaded images, ingest attachments, PayNow QR images, delivery photos. Presigned URLs default to 1 h.

## PDF (`src/common/services/pdf-generator.service.ts`)

Headless Puppeteer (`--no-sandbox`…), 1200×1600 viewport, A4 zero-margin print CSS. Setup notes: `api-server-production/docs/PDF_GENERATION_SETUP.md`.

## Public payment links

`DocumentsService.ensurePayToken()` idempotently writes `config.payToken` and builds `${PORTAL_BASE_URL || 'https://www.ai-ms.io'}/pay/{token}`. The link becomes the invoice email's "Click to Pay" button; `GET /public-pay/:token` serves the public page data (amount, status, org branding, bank details, presigned PayNow QR, PDF URL).

## WhatsApp

Meta Cloud API (Tech Provider / Embedded Signup) — full detail in [External Surface](/backend/modules-external). Env: `META_APP_ID`, `META_APP_SECRET`, `WHATSAPP_WEBHOOK_VERIFY_TOKEN`, `WHATSAPP_API_VERSION` (default `v23.0`), `WHATSAPP_GROUP_BRIDGE_TOKEN`.

**Email matching priority (round T, 2026-10).** `email-match.rules.ts` decides in this order — the first cue that names one record wins, the rest only add `notes`: attachment hard key › own-text hard key › subject hard key › own-text product cues › thread link (most recent accepted message; a combined thread follows the one the own text, else a single-product subject, describes) › subject cues (tie-break) › quoted history (never decides; a last-resort weak suggestion). `check` (the "Check — subject disagrees" chip) holds REAL conflicts only: a subject naming exactly one product whose grade / size / qty / customer contradicts the decision; a multi-product subject is never a conflict; a stale month is a note against a hard key. Cues are normalised (6005C ≈ 6005, 8インチ ≈ 203 MM, 40T ≈ 40.271 t within ±10 %). `MatchDecision.source` says which cue decided. Round U: `autoTier(decision, thread)` → `high` (hard key in an attachment / own text, no conflict, no other order) or `medium` (thread / cue decision agreeing with the thread's most recent accepted link); the live intake applies both by itself behind `enableEmailReasoner`, into empty slots only (`slotsFree`, `REPEATABLE_DOC_TYPES`), labelled `reviewed · …`; the backlog one-off is `scripts/_email-autoapply.ts --org=<id> [--apply]`. Round V adds order-level cues (`orderCuesMatch`, `productSegments`: customer + delivery month + grade + total qty ±10 % → the order; several products → `links`), exact-tonnage keys (`KeyHit.kind = 'net'`), the attachment-vs-own-key split (the email links where its words point; attachments file where their content names), link-only replies inheriting the thread's records (`INHERIT_THREAD`, "thread covers") and General for contact messages from a known counterparty. Candidates carry a per-record reason ("B/L … in the attachment", "… only in quoted history", "subject only"). Read-only analysis / dry re-run: `scripts/_email-reason-analysis.ts --org=<id> [--after]`.

**No wrong links (round W, 2026-10-22).** `MatchDecision.sources` lists every INDEPENDENT place that agrees with the target (`attachment` · `own-text` · `subject` · `thread`; a key and product words in the same text are one source) and `autoTier` needs TWO of them (`high` when a hard key is among them, else `medium`); the legacy PARTIAL_AUTO guards also require two sources whenever the plan files a document or fills a field, and never replace a single-slot document (`slotsFree`). The AI reasoner's verified answer counts as one source: it applies by itself only when the thread, a rules key hit or the order-level cues agree, else its answer becomes the suggestion. `EmailTriageService.reason(…, { independent: true })` is the SECOND PASS — the model never sees the email's current link nor any link AIMS applied by itself (only links a person confirmed / changed); `secondPass(org, logId)` compares it with the hard evidence (`email-audit.ts` → AGREE · AGREE_WEAK · NO_ANSWER · DISAGREE_CLEAR · DISAGREE_UNCLEAR · NOT_OPEN). `selfCheck()` (cron 03:47, orgs with `enableEmailReasoner`) re-runs it on every AUTO-reviewed email of the last 7 days and sends a disagreement back to Unprocessed as a RECHECK question (`sendBackAsQuestion`: files undone, `actions.question`); the one-off audit is `scripts/_email-audit.ts --org=<id> [--apply-clear] [--apply-unclear] [--inspect=<subject>]`.

**Question cards (round W).** `email-question.ts` (pure, EN/JA) turns a thread's newest unprocessed message into one card (`questionOf` → CONFIRM · WHICH · CHECK · NEW_DEAL · IS_SHIPMENT · RECHECK: title, "what AIMS found", record options with summary + why, extras). `GET /email-inbox/threads?tab=UNPROCESSED&lang=ja|en` returns `question`, `answerIds` (the thread's unprocessed ids) and `earlier` per thread, and `counts.snoozed`; `POST /email-inbox/answer {ids, answer}` applies one answer to every id (`record` → assign + accept; `not_shipment` / `not_deal` → HIDDEN, never deleted; `later` → `actions.snoozedUntil` +1 day) and returns the banner text; `POST /email-inbox/answer/undo {ids, kind}` reverses it. WhatsApp: `notifyNeedsMe` sends `questionWhatsAppText` (numbered options, "Reply 1, 2 or 3 · 0 = ask later · X = not a shipment") in the user's language; a bare number / X reply answers the last NEEDS_ME question sent to that number within 24 h (`ShipmentsToolsService.answerNumbered`). Sender companies: `email-companies.ts` (`companyOf(from, overrides)` — domain → name, overrides in `TradeSetting.docDefaults.emailCompanies`, edited in Settings → Email filter → Companies).

**Email view (round T).** `GET /email-inbox/:id/message` parses the stored `.eml` (`email-mime.ts`: MIME tree, QP / base64, RFC 2047, ISO-2022-JP / Shift_JIS) and returns headers, own text, quoted text, the raw HTML with remote content defused (`blockRemoteContent`: scripts / forms / meta / link removed, remote `src` → `data-aims-src`) and 1-hour attachment URLs; `GET /email-inbox/:id/thread` the thread oldest → newest. The portal sanitises again (DOMPurify allowlist) and renders in `<iframe sandbox="">` with a no-network CSP; "Load images" restores https images only.

**Staff assistant (AIMS Operator).** A WhatsApp number set on a user's org member profile (User Management → Users → Edit → WhatsApp) links that number to the Clerk user; the Operator (`src/operator/`) then acts with exactly that user's permissions, writes go through Confirm / Cancel cards, and every action lands in the Activity Log as the user (`channel: chat:whatsapp`). Orgs with the SHIPMENTS module on (ADH, round S 2026-10; round T made it a full assistant) get the **shipments profile** instead of the generic tool set: `shipments-tools.service.ts` — 28 tools: read (emails recent / find / full text, record status, arrivals, shipments by step, orders list, tasks, needs-me, list + send documents, draft-reply facts), money (`shipments:money` only: order earnings, totals from `TradeAdminDashboardService`, record a payment on a paying step), confirm-first writes (email link / not-shipment, task done / snooze, custom reminders, ETA / vessel / B/L / arrival, add shipment, create order (details or from a PI file), step done, note, draft generated document + PDF preview); a PDF or photo goes through the email intake, a caption naming a record is a link hint, gated by the org flag `enableWhatsAppAgent` (off = linked staff are ignored and logged). Pushes: `ShipmentsNotifyService` (queue, per-user prefs `whatsappPrefs`: digest / needs-me / filed / events, quiet hours JST, digest language) → `WhatsAppOutbox` → `ShipmentsOutboxService` (cron every minute: 08:30 JST digest as the `aims_notify` template, due rows batched into one text per user, sent on the line the user last wrote to).

## water-sg (SIDS/ECM/ESS) — bidirectional

- **Outbound**: `WaterSgService`/`WaterSgLinkService` create sites on DO sign-off when `enableWaterSgSites` is enabled (`WATER_SG_API_URL`, `WATER_SG_ECM_API_URL`, `WATER_SG_ESS_API_URL`, `WATER_SG_API_KEY`).
- **Inbound**: `/public-api/*` guarded by the separate `WATER_SG_INBOUND_API_KEY`.
- Spec: `WATER_SG_INTEGRATION.md` at repo root.

**Round X (2026-10-22) — WhatsApp pushes and the email pop-up.** Pushes are short, plain and emoji-free: the 08:30 JST digest lists the auto-filed count, how many questions need a check (the Dashboard's own number: questions and the emails behind them), overdue tasks and this week's arrivals, then the Dashboard link; an email needing a check is pushed as "From / Subject / what AIMS isn't sure about / Reply 1 for …, 2 for …, or check it on the Dashboard", several within ten minutes as one message with one line each; a possible new deal and the nightly re-check have their own short forms; events are one line each. The text lives in `src/operator/push-text.ts` (pure, EN/JA). The digest goes out as plain text (the closed-window recovery resends it through the bridge or the `aims_notify` template); `scripts/whatsapp-templates.ts --show|--list|--submit` holds the structured utility templates (one variable per line) to submit to Meta, and `WHATSAPP_DIGEST_TEMPLATE` switches the digest to the approved one. Cards: an email with a known record number anywhere (quoted text included) is never a "new deal" card; a reply about existing shipments asks which shipment. The portal opens the full email in a pop-up dialog and counts "N questions (M emails)" everywhere.

**Round Z (2026-10-22) — the Sales dashboard at the portal home.** `/portal` renders the active org's own dashboard: the Sales dashboard (Overview / Admin, emails waiting, filed automatically, tasks, arrivals; `?view=emails` for the full email view) when the org has the SHIPMENTS module, the asset dashboard otherwise, with no redirect. `/portal/shipments/dashboard` and `/portal/shipments/inbox` are permanent redirects in `next.config.mjs` (query kept). WhatsApp push links point at `/portal` (digest, events) or `/portal?view=emails` (email questions), with `?aorg=<org>` so an admin's link opens under ADH; the pending Meta templates take the link as a parameter, so nothing is resubmitted. The ADH org's DASHBOARD module row points at `/portal` (`scripts/setup-adh-org.ts`).

**Round AA (2026-10-22) — confirm-first answers.** A question card shows only the question, a "From Company · date · subject" line and two buttons; the Choose-shipment dialog (search, checkbox list with the likely shipments first, "Not about a shipment" / "New deal → Create order" / "Ask later", Confirm) is the only way to answer, and `POST /email-inbox/answer` now accepts `answer.targets` (up to 10 shipments; the email is linked to all of them). On WhatsApp the shipment question asks for the shipment number; a reply like `18-1 18-2` becomes a pending `email_answer` action with a Confirm / Cancel card (`ShipmentsToolsService.pendingForRefs`), applied only on the tap.
